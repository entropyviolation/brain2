Intelligent Agents

What is an agent, and what makes one rational?

1.1Agents and Environments

Core definition

An agent is anything that perceives its environment through sensors and acts on it through actuators. That's the whole abstraction — a loop of percept in, action out.

Three quick instances make it concrete. A human: sensors are eyes and ears; actuators are hands, legs, and voice. A robot: cameras and lidar in; motor commands out. A software agent: keystrokes, files, network packets, and API responses in; screen output, file writes, and network requests out.

A single snapshot of input is a percept; the complete history of everything the agent has ever perceived is its percept sequence. A key principle: an agent's choice of action can depend on its entire percept sequence, but never on things it hasn't perceived. If we specify the action for every possible percept sequence, we've fully characterized the agent's external behavior.

Agent function vs. agent program

The agent function is the abstract mathematical mapping from percept sequences to actions — imagine an (often infinite) lookup table listing what the agent does after every possible history. The agent program is the concrete implementation running on real hardware that realizes that function. One function can be implemented by many programs; keeping the two ideas separate is essential. The function is the what; the program is the how.

Worked example · The vacuum world

The classic toy world: two squares, A and B. Each may contain dirt. The vacuum agent perceives its current location and whether that square is dirty; its actions are Left, Right, Suck, and NoOp.

A simple agent function, written as a partial table:

Percept sequence (latest percept)Action
[A, Clean]Right
[A, Dirty]Suck
[B, Clean]Left
[B, Dirty]Suck
[A, Clean], [A, Clean]Right
[A, Clean], [A, Dirty]Suck

In words: if the current square is dirty, suck; otherwise move to the other square. The table continues forever (one row per possible percept sequence), but the rule that generates it fits in one line — that's exactly the gap between agent function (table) and agent program (rule).

2026 update

The toy vacuum grew up. A modern robot vacuum builds a lidar/SLAM map of your home, tracks where it has cleaned, and estimates dirt via optical and acoustic sensors — it's a model-based agent (Section 1.5) operating in a partially observable, continuous environment. And today's LLM-based "agents" fit the same abstraction perfectly: percepts are user messages and tool results; actuators are text output and tool/API calls. The framework from the 1990s describes them without modification.

Checkpoint · 1.1
  • An agent = sensors + actuators + something in between; it maps percept sequences → actions.
  • The agent function is the abstract external description; the agent program is the running implementation.
  • Agents can only condition behavior on what they've actually perceived.

1.2Good Behavior: Rationality

Which rows of the table are the right ones? We need a yardstick. A performance measure evaluates the sequence of environment states the agent's behavior produces. Crucially, it scores environment states, not agent states — otherwise an agent could "succeed" by deluding itself that it did a great job.

Design pitfall

Design the measure for what you actually want in the world, not for how you think the agent should behave. Reward a vacuum for "amount of dirt sucked up" and a clever agent will suck dirt, dump it back out, and suck it again forever. Reward "clean floor per time step, minus energy and noise penalties" instead. (This is the ancestor of today's reward hacking and AI alignment problems: mis-specified objectives get optimized literally.)

Definition of rationality

For each possible percept sequence, a rational agent selects the action expected to maximize its performance measure, given the evidence in the percept sequence and whatever built-in knowledge it has.

Rationality thus depends on four things: (1) the performance measure, (2) the agent's prior knowledge of the environment, (3) the actions available, and (4) the percept sequence so far. Under a measure that awards one point per clean square per time step, with known geography and unknown dirt placement, the simple vacuum rule above is rational. Change the assumptions — say, add a penalty per movement — and it stops being rational (it oscillates pointlessly once everything's clean; a rational agent would learn to sit still).

Rational ≠ omniscient, and the case for learning

  • Omniscience is not required. An omniscient agent knows actual outcomes; a rational agent maximizes expected outcome. Crossing an empty street and being hit by falling debris is bad luck, not irrationality. Rationality is judged on what could reasonably be expected.
  • Information gathering is rational. Looking both ways before crossing is an action whose value is that it improves future percepts. Exploration — as when an agent probes an unknown environment — is the same idea at larger scale.
  • Learning is required whenever the environment isn't fully known in advance. Agents that never modify their behavior from experience are fragile: the dung beetle keeps performing its ball-plugging routine even when the ball is removed mid-task, and the sphex wasp will re-run its "check the burrow" subroutine indefinitely if its prey is moved — behavior that looks smart but can't adapt.
  • Autonomy means relying on one's own percepts and learning rather than solely on the designer's prior knowledge. A rational agent should become effectively independent of its initial programming as experience accumulates — reasonable initial knowledge plus the ability to learn.
Checkpoint · 1.2
  • Rational = maximizes expected performance given percepts + prior knowledge. Not perfection, not omniscience.
  • Performance measures should score world outcomes, and mis-specified measures get gamed.
  • Gathering information, exploring, and learning are themselves rational actions; autonomy grows as learning replaces built-in assumptions.

1.5The Structure of Agents: Five Architectures

The job of AI is to write the agent program. Everything runs on some architecture (hardware + sensors + actuators): agent = architecture + program. A table-driven program is a non-starter — for chess the lookup table would need at least 10150 entries — so the real question is how to produce rational behavior from compact programs. Four basic designs, plus learning, in increasing generality:

1 · Simple reflex agents

Act on the current percept only, via condition–action rules: if car-in-front-is-braking then initiate-braking. Tiny and fast, but correct only when the right decision is always derivable from the current percept — i.e., only in fully observable settings. A reflex vacuum without a location sensor can't decide between Left and Right and may loop forever; randomizing its choice can rescue it (an escape hatch that matters again in multi-agent worlds), but a smarter deterministic agent usually does better.

2 · Model-based reflex agents

Handle partial observability by keeping internal state, updated using a model of (a) how the world evolves on its own and (b) what the agent's actions do. "Where's the car I overtook a moment ago?" — you can't see it, but your model says it's beside you. The internal state is the agent's best guess; certainty is impossible under partial observability, and that's fine.

3 · Goal-based agents

Knowing the current state isn't enough at a fork in the road — the right action depends on where you're going. Goal-based agents combine the world model with explicit goal information and choose actions predicted to achieve the goal, possibly via long search and planning sequences (Units 2–3). The payoff over hard-wired reflexes is flexibility: change the goal (new destination) or the model (rain → brakes grip differently) and behavior updates automatically, instead of requiring dozens of rewritten rules.

4 · Utility-based agents

Goals are binary (achieved or not); real trade-offs need a utility function — an internalization of the performance measure that scores how desirable each state is. Utility handles (a) conflicting goals (speed vs. safety) and (b) uncertainty: a rational agent maximizes expected utility, weighting each outcome's utility by its probability. This is the architecture that connects agent design to decision theory.

5 · Learning agents

Any of the above can be wrapped in a learning loop with four parts: the performance element (the whole agent as described so far), a critic that judges outcomes against a fixed performance standard, a learning element that uses that feedback to improve every component (model, rules, utility estimates), and a problem generator that proposes exploratory actions — deliberately suboptimal in the short run — to gather informative experience. A taxi that gets honked at (critic) learns not to cut across three lanes (learning element), and occasionally tries a new route (problem generator).

2026 update

These layers map cleanly onto modern systems. A thermostat is a simple reflex agent. A robot vacuum's SLAM map is model-based state. A chess engine is goal/utility-based search. Reinforcement-learning systems (AlphaGo, RLHF-trained models) are literally the learning-agent diagram: reward signal = critic, gradient updates = learning element, exploration policies = problem generator. Tool-using LLM agents are goal-based agents whose "model" and "rules" are learned implicitly in the network's weights.

How agents represent state: three levels

  • Atomic: each state is an indivisible black box with no internal structure — city "B" is just B. Search and game-playing (Unit 2), hidden Markov models, and MDPs work atomically.
  • Factored: a state is a vector of variables/attributes (fuel level, GPS coordinates, oil light). Two states can share some attributes — enabling constraint satisfaction, propositional logic, planning, and Bayesian networks.
  • Structured: states contain objects and relations ("a truck is backing into the dairy's driveway, blocked by a loose cow") — the territory of first-order logic, relational databases, and much of natural language understanding.

Expressiveness increases along the axis atomic → factored → structured: more expressive representations capture the same information more concisely, but reasoning and learning get harder. Real systems often mix levels.

Checkpoint · 1.5 (end of Unit 1)
  • Agent-program ladder: reflex → model-based → goal-based → utility-based, each fixing a limitation of the last; learning wraps any of them.
  • Partial observability ⇒ internal state; futures that matter ⇒ goals; trade-offs and uncertainty ⇒ expected utility.
  • State representations: atomic / factored / structured — a trade of expressiveness against tractable reasoning.
  • Unit 2 builds the machinery inside goal-based agents: search.

Solving Problems by Searching

Deterministic, observable, static, known environments

2.1Problem-Solving Agents

A problem-solving agent is a goal-based agent that uses atomic state representations and finds a sequence of actions leading to a goal. Its life cycle: formulate a goal and a problem, search for a solution, then execute the plan — in the simplest case with its "eyes closed," ignoring percepts during execution (an open-loop system), which is safe exactly when the environment is deterministic, fully observable, static, and known.

Running example · Touring Romania

An agent is in Arad, Romania, with a nonrefundable flight out of Bucharest tomorrow. Goal formulation: be in Bucharest (goals filter the infinity of possible objectives down to something actionable). Problem formulation: decide the granularity — the right level here is driving between cities, not "rotate steering wheel 3° left." Without a map, the agent must act randomly; with a map (a known environment), it can simulate journeys internally and commit to the best one before moving. This "plan on a map" setup is precisely what your phone's navigation app does — over a graph with hundreds of millions of road segments instead of twenty cities.

A well-defined problem has five components
  1. Initial state — e.g., In(Arad).
  2. Actions — the actions applicable in each state: from Arad, Go(Sibiu), Go(Timisoara), Go(Zerind).
  3. Transition model — Result(state, action): the state each action produces. Together, 1–3 implicitly define the state space, a graph of states connected by actions; a path is a sequence of actions.
  4. Goal test — is a given state a goal? Can be a set membership check ({In(Bucharest)}) or an abstract property (checkmate).
  5. Path cost — a nonnegative number scoring each path, usually a sum of step costs c(s, a, s′) — kilometers, time, or money.

A solution is a path from initial state to a goal state; an optimal solution has minimal path cost.

Abstraction is what makes formulation work: we strip out the radio, the scenery, and the weather because they're irrelevant to reaching Bucharest. A good abstraction is valid (any abstract solution expands into a real one) and useful (the abstract steps are easier to carry out than the original problem). Without abstraction, agents drown in detail.

Checkpoint · 2.1
  • Cycle: formulate → search → execute; open-loop execution needs a benign environment.
  • A problem = initial state + actions + transition model + goal test + path cost; solution = path to a goal; optimal = cheapest such path.
  • Choose the abstraction level deliberately — it defines the state space you'll search.

2.2Example Problems

Toy problems (crisp, comparable across algorithms):

  • Vacuum world: 2 squares × agent location × dirt configuration = 8 states (n·2n in general); actions Left/Right/Suck; goal: all clean.
  • 8-puzzle: a 3×3 board with eight numbered tiles and a blank; actions = move the blank Left/Right/Up/Down; goal: a specified tile arrangement; step cost 1. It has 9!/2 = 181,440 reachable states (exactly half of all arrangements are reachable — a parity argument splits the states into two disjoint sets). The 15-puzzle has ~1.3 trillion states; the 24-puzzle ~1025. Sliding-tile puzzles are the standard testbed for heuristics (Section 2.6). Note the formulation quietly abstracts away physical details like whether you shove two tiles at once.
  • 8-queens: place 8 queens on a chessboard so none attacks another. Two formulation styles matter more than the puzzle itself: an incremental formulation adds one queen per action (naively 1.8×1014 sequences; restricting each queen to the leftmost empty column and non-attacked squares cuts this to 2,057 — formulation choices change search difficulty by ten orders of magnitude); a complete-state formulation starts with all 8 queens on the board and moves them (the natural fit for local search, Unit 3).
  • Knuth's conjecture: starting from 4 and applying factorial, square root, and floor, you can reach any positive integer — e.g., floor(√√√√√((4!)!)) = 5. Its lesson: state spaces can be infinite even with trivial rules.

Real-world problems:

  • Route finding: driving directions, airline travel planning (states = airport + time + fare context; costs mix money, time, seat quality, delay risk), network routing, military logistics. Modern mapping services solve continent-scale versions in milliseconds using heavily precomputed variants of the algorithms below.
  • Touring problems ("visit every city at least once"): the state must include the set of cities visited, not just the current city.
  • Traveling salesperson problem (TSP): visit each city exactly once, minimizing tour length — NP-hard, yet enormous instances (chip fabrication, delivery-fleet routing, telescope scheduling) are handled well by the local-search methods of Unit 3.
  • VLSI layout: placing millions of components and routing wires on a chip — cell layout + channel routing as search/optimization. (Today, RL and learned methods assist chip floorplanning, but the problem formulation is unchanged.)
  • Robot navigation: route finding generalized to continuous spaces with potentially infinite action sets and extra dimensions for arm joints.
  • Automatic assembly sequencing / protein design: find an ordering (or amino-acid sequence) satisfying geometric or chemical constraints — checking a single step may itself require expensive geometric search.
Checkpoint · 2.2
  • Toy problems calibrate algorithms; real problems pay the bills. The same five-part formulation covers both.
  • How you formulate matters as much as how you search (8-queens: 1014 → 2,057 states).

2.3Searching for Solutions: Trees, Graphs, and Bookkeeping

Search algorithms explore the state space by growing a search tree: the root is the initial state; expanding a node applies each legal action to generate child nodes. The set of generated-but-unexpanded leaves is the frontier (open list). Every search algorithm is a choice of which frontier node to expand next — the search strategy.

function TREE-SEARCH(problem) returns a solution or failure
  frontier ← {node(problem.INITIAL-STATE)}
  loop:
    if frontier is empty then return failure
    node ← POP(frontier)            // strategy = which node comes out
    if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
    frontier ← frontier ∪ EXPAND(node)

function GRAPH-SEARCH(problem)     // same, plus:
  explored ← ∅
  ... add node.STATE to explored when popped;
  ... only add children whose state is not in frontier ∪ explored

Why the extra bookkeeping? Repeated states. In Romania, Arad→Sibiu→Arad is a loopy path; more generally any redundant path (a worse way to reach a state you can reach better) wastes work. In a rectangular grid, each state has ~4 successors, so a depth-d tree has ~4d leaves — but only ~2d² distinct states lie within d steps. Tree search can turn a linear-sized problem into an exponential one. GRAPH-SEARCH's explored set (closed list) eliminates all redundant paths at the price of memory, and maintains a clean invariant: the frontier separates the explored region from the unexplored region, so every path from start to an unexplored state must pass through the frontier.

Node bookkeeping. A node is not a state: a node is a path-bookkeeping object with four fields — STATE, PARENT, ACTION (the action that generated it), and PATH-COST g(n). Two nodes can hold the same state via different paths. The frontier is a queue: FIFO → breadth-first, LIFO (stack) → depth-first, priority queue → uniform-cost and friends.

Judging a search algorithm
  • Completeness — guaranteed to find a solution if one exists?
  • Optimality — guaranteed to find the cheapest solution?
  • Time complexity — nodes generated, in terms of b (branching factor), d (depth of shallowest goal), m (max depth of the space).
  • Space complexity — max nodes held in memory.

Total cost of problem-solving = search cost (time/memory) + path cost of the solution found.

Checkpoint · 2.3
  • Search = grow a tree over the state space; the frontier ordering defines the algorithm.
  • Graph search adds an explored set to kill redundant paths — essential whenever the space has cycles or a grid structure.
  • Evaluate on completeness, optimality, time, space using b, d, m.

2.4Uninformed (Blind) Search

Uninformed strategies use only the problem definition — no sense of which non-goal state is "more promising."

Breadth-first search (BFS)

FIFO frontier: expand the shallowest node first, sweeping the tree level by level. Apply the goal test at generation time (not expansion) to save a whole level of work. Complete (if b is finite) and optimal when all step costs are equal (it finds the shallowest goal, which is then the cheapest). Time and space are both O(bd) — and space is the killer: at b = 10, generating 1M nodes/sec at 1 KB/node, depth 12 takes 13 days and 1 petabyte of memory. Two morals: memory usually fails before time, and exponential blowup can't be out-waited — depth 16 would take 350 years even with unlimited RAM.

Uniform-cost search (UCS)

Priority queue ordered by path cost g(n): always expand the cheapest known path. Two twists versus BFS: the goal test happens at expansion (a goal first generated via a costly path might later be reachable cheaply), and a frontier node is replaced if a cheaper path to its state appears. In Romania, going Sibiu→Rimnicu(80)→Pitesti(177)→Bucharest(278) beats the tempting direct Sibiu→Fagaras(99)→Bucharest(310) — UCS discovers this automatically. Complete and optimal for any step costs ≥ ε > 0 (it expands nodes in order of optimal path cost). Complexity O(b1+⌊C*/ε⌋) where C* is the optimal cost — potentially worse than bd when many tiny steps exist, and UCS examines all paths cheaper than C* before committing. This is Dijkstra's algorithm wearing an AI hat.

Depth-first search (DFS)

LIFO frontier: dive down the deepest branch, backtrack on dead ends. Graph-search DFS is complete in finite spaces; tree-search DFS can loop forever, and both fail in infinite spaces. Not optimal. Time O(bm) — possibly far worse than bd. So why care? Space: O(bm), linear! Once a subtree is fully explored it can be forgotten. At depth 16 where BFS needed exabytes, DFS needs ~156 KB. A backtracking variant generating one successor at a time (and modifying/undoing state in place) needs only O(m) — vital in robotics and other memory-starved domains. DFS is the workhorse inside constraint satisfaction, SAT solving, and logic programming.

Depth-limited and iterative deepening

Depth-limited search caps DFS at depth ℓ (incomplete if ℓ < d; still not optimal). Good limits sometimes come from domain knowledge — e.g., the diameter of the state space (any Romanian city reaches any other within 9 steps). Iterative deepening search (IDS) runs depth-limited search with ℓ = 0, 1, 2, … until a goal appears. It looks wasteful — the top of the tree is regenerated repeatedly — but the bottom level dominates exponentially: nodes at the deepest level are generated once, the next level twice, and so on, giving N(IDS) = (d)b + (d−1)b² + … + (1)bd. At b = 10, d = 5: IDS generates 123,456 nodes vs. 111,111 for BFS — about 11% overhead. IDS is complete, optimal for unit costs, time O(bd), space O(bd).

Rule of thumb

IDS is the default uninformed method for large spaces with unknown solution depth — BFS-quality answers at DFS memory prices. (Cost-sensitive analog: iterative lengthening with increasing cost limits — clean idea, but it adds substantial overhead over UCS.) A hybrid also works: run BFS until memory is nearly full, then IDS from the frontier.

Bidirectional search

Search forward from the start and backward from the goal until the frontiers touch; the motivation is arithmetic — bd/2 + bd/2 ≪ bd (at b=10, d=6: 22,200 nodes vs. 11.1M). Requires the goal-test to become a frontier-intersection check (do it on generation), keeping at least one frontier in memory (space O(bd/2) — its main weakness), and the ability to compute predecessors. It's awkward when the "goal" is an abstract property like checkmate, and with many explicit goal states you search backward from a dummy state adjacent to all of them.

2.5Informed Search: Greedy and A*

Informed (heuristic) search exploits problem-specific knowledge via an evaluation function f(n) that ranks frontier nodes (a priority queue on f — the general pattern called best-first search). The knowledge enters through a heuristic function:

Heuristic

h(n) = estimated cost of the cheapest path from n's state to a goal. Depends on the state only; h(goal) = 0. For Romania: hSLD = straight-line distance to Bucharest — computable from coordinates, unavailable from the problem definition itself, and clearly correlated with true road distance.

Greedy best-first search

Set f(n) = h(n): always expand the node that looks closest to the goal. From Arad it darts Sibiu → Fagaras → Bucharest — a solution found with minimal expansion, but a suboptimal one (310 km vs. the optimal 278 via Rimnicu/Pitesti). Worse, greed can be badly misled: seeking Fagaras from Iasi, the heuristic points at Neamt, a dead end, and tree-search greedy oscillates Iasi↔Neamt forever. Greedy is incomplete (tree version), not optimal, worst-case O(bm) time/space — but often excellent in practice with a good heuristic.

A* search

The big idea

f(n) = g(n) + h(n) — cost already paid to reach n, plus estimated cost still to go = estimated cost of the cheapest solution through n. Expand the node with lowest f. With the right conditions on h, A* is complete and optimal — arguably the most famous algorithm in AI, powering everything from game pathfinding to robot motion planning.

Two conditions on h:

  • Admissible: h(n) never overestimates the true remaining cost — it's optimistic. (Straight-line distance is admissible: no road is shorter than the crow flies.) Admissibility ⇒ tree-search A* is optimal.
  • Consistent (monotone): h(n) ≤ c(n, a, n′) + h(n′) for every successor n′ — a triangle inequality. Consistency ⇒ admissibility, and ⇒ graph-search A* is optimal. Almost every natural admissible heuristic is also consistent.

Why it works (proof sketch): with consistent h, f-values are nondecreasing along any path (f(n′) = g(n′)+h(n′) ≥ g(n)+h(n) = f(n)), and whenever A* expands a node it has already found the optimal path to that node's state. So A* expands nodes in nondecreasing f order; the first goal expanded must be optimal — every other frontier node has f at least as large, and f at a goal equals true cost. Picture contours of equal f spreading through the state space like elevation lines: A* fans out through all nodes with f < C* (the optimal cost), some nodes with f = C*, and never any node with f > C* — those are pruned without inspection. This pruning-with-a-guarantee is the essence of A*, and A* is optimally efficient among such algorithms: any algorithm that guarantees optimality using the same heuristic must expand every node with f < C* too, or risk missing a cheaper solution.

On the Romania problem, A* expands Rimnicu before Fagaras (f 413 vs 415), briefly reaches Bucharest via Fagaras at f = 450, but doesn't stop — it expands Pitesti (f 417) first and uncovers the 418 route. Greedy's mistake, fixed by accounting for g.

The catch

A* keeps all generated nodes in memory, and for most problems the number of nodes inside the goal contour is still exponential: unless the heuristic's error grows no faster than the log of the true cost (|h − h*| ≤ O(log h*)), which almost never holds in practice, A* runs out of memory long before it runs out of time. Hence the memory-bounded family below. Also: computing a cleverer h costs time per node — a trade-off, not a free lunch.

Memory-bounded heuristic search

  • IDA* — iterative deepening with an f-cost cutoff instead of a depth cutoff; each iteration's new cutoff is the smallest f that exceeded the old one. Linear memory; practical for unit-step-cost problems like sliding-tile puzzles; struggles when f takes many distinct real values.
  • RBFS (recursive best-first) — DFS-like recursion that remembers, for each abandoned subtree, the best f seen there (backed-up value), and jumps back when the current branch exceeds the best alternative. Linear space O(bd), optimal with admissible h, but can thrash — re-generating forgotten subtrees as its "mind changes" between branches.
  • SMA* (simplified memory-bounded A*) — plain A* until memory fills, then drop the worst leaf (highest f), backing its value up into its parent so the subtree can be regenerated later only if everything else proves worse. Complete if any solution fits in memory; optimal if any optimal solution fits. On hard problems it can thrash between candidate paths — memory limits can make a problem intractable in time even when it's solvable in principle.
Checkpoint · 2.5
  • Greedy (f = h): fast, fallible. A* (f = g + h): complete + optimal given admissible (tree) / consistent (graph) h.
  • A* expands exactly the nodes with f < C* (plus some at C*) — optimal efficiency, but exponential memory in general.
  • Memory-bounded variants — IDA*, RBFS, SMA* — trade regeneration time for linear/bounded space.

2.6Heuristic Functions: Where h Comes From

The 8-puzzle (average optimal solution ≈ 22 steps, b ≈ 3, so ~322 ≈ 3.1×1010 tree-search states) is the classic proving ground. Two standard admissible heuristics:

  • h₁ = number of misplaced tiles — every misplaced tile needs ≥ 1 move.
  • h₂ = sum of Manhattan distances of each tile from its goal position — every tile needs at least that many moves.
Worked example · Measuring heuristic quality

Define the effective branching factor b*: if A* generates N nodes solving at depth d, b* is the branching factor a uniform tree would need for N+1 = 1 + b* + (b*)² + … + (b*)d. A heuristic is good if b* is near 1. Empirically over random 8-puzzles at solution depth 12: IDS generates ~364,404 nodes (b* ≈ 2.78); A*(h₁) ~227 (b* ≈ 1.42); A*(h₂) ~73 nodes (b* ≈ 1.24). At depth 24, IDS is hopeless (~54 billion nodes) while A*(h₂) needs ~1,641. Small heuristic improvements compound exponentially with depth.

Domination: h₂(n) ≥ h₁(n) for all n, so h₂ dominates h₁ — and domination translates directly into fewer expansions (every node with f < C* under the bigger h is also expanded under the smaller). Rule: among admissible heuristics, bigger is always better (modulo compute cost per node and consistency).

Three factories for admissible heuristics

  1. Relaxed problems. Drop restrictions from the action rules; the optimal cost of the relaxed problem is an admissible (and, satisfyingly, automatically consistent) heuristic for the original, because the relaxed state space is a supergraph of the real one — removing rules only adds edges. If a tile could hop anywhere → h₁. If a tile could move to any adjacent square regardless of occupancy → h₂. Given a formal problem description, relaxations can even be generated automatically (the ABSOLVER program derived new 8-puzzle heuristics and the first useful Rubik's-Cube heuristic this way). The relaxed problem must be easy to solve exactly, or the heuristic costs too much to compute. With several relaxations giving h₁…hm, take h = max(h₁,…,hm) — still admissible, dominates each component.

  2. Pattern databases. Precompute and store the exact solution cost of every configuration of a subproblem — e.g., just tiles 1-2-3-4 (other tiles wildcarded) — by searching backward from the goal. At search time, look up the current pattern's cost: an admissible heuristic. Multiple databases (1-2-3-4, 5-6-7-8) can be maxed; disjoint pattern databases count only each subset's own tile moves so the values can be added while staying admissible — yielding ~1000× speedups on the 15-puzzle and making random 24-puzzles solvable in hours. This idea (plus huge compute) is how Rubik's Cube solvers proved "God's number" is 20.

  3. Learning from experience. Solve many instances, then learn a model h(n) from state features (e.g., "number of misplaced tiles," "number of adjacent tile pairs also adjacent in the goal") via regression or a neural network. Learned heuristics often work well but usually forfeit admissibility/consistency guarantees. This thread runs straight to modern AI: AlphaGo-style systems are best-first search (MCTS) guided by a learned evaluation function — the same architecture, with the heuristic learned by a deep network.

Checkpoint · 2.6 (end of Unit 2)
  • Heuristic quality is measured by effective branching factor; dominating heuristics strictly reduce work; effects compound exponentially with depth.
  • Get admissible heuristics from relaxed problems (take the max of several), pattern databases (add disjoint ones), or learning.
  • Unit 2's world was deterministic, observable, static, known. Unit 3 removes those crutches one at a time.

3.1Local Search and Optimization

Classical search returns a path — but for 8-queens, VLSI placement, factory scheduling, or TSP, only the final configuration matters. Local search keeps just a current state (no frontier, no paths, no explored set) and moves to neighboring states, using O(1) memory and often finding good states in enormous or continuous spaces where systematic search drowns. The same machinery solves pure optimization problems: find the state maximizing an objective function. Picture the state-space landscape — location = state, elevation = objective value — and the task is finding the global maximum among distracting local maxima, flat plateaus (including shoulders that do eventually rise), and ridges (sequences of local maxima that are easy to walk along but where every single step available goes downhill).

Hill climbing (steepest ascent)

function HILL-CLIMBING(problem) returns a local-maximum state
  current ← problem.INITIAL-STATE
  loop:
    neighbor ← highest-valued successor of current
    if VALUE(neighbor) ≤ VALUE(current) then return current
    current ← neighbor
Worked example · 8-queens by local search

Complete-state formulation: one queen per column (88 ≈ 17M states); a move slides one queen within its column (8×7 = 56 neighbors per state); objective = minimize h = number of attacking pairs (h = 0 is a solution). Hill climbing greedily picks the move that most reduces h. Results from random starts: it solves only ~14% of instances (86% get stuck at local minima) — but it's blisteringly fast, averaging just ~4 steps to succeed and ~3 to get stuck, in a space of 17 million states. Fixes:

  • Sideways moves (allow equal-h moves, capped at, say, 100 consecutive) — lets the search drift across shoulders: success jumps to 94%, at ~21 steps per success.
  • Random-restart hill climbing — if at first you don't succeed, restart from a new random state. With success probability p per attempt, expected restarts = 1/p; for 8-queens (p ≈ 0.14) that's ~7 cheap attempts. It even makes 3-million-queens solvable in under a minute. Random restarts make hill climbing complete with probability approaching 1.

Variants: stochastic hill climbing picks randomly among uphill moves (slower, sometimes finds better optima); first-choice hill climbing generates random successors until one beats the current state — the right move when states have thousands of neighbors. Success depends on landscape shape: NP-hard problems typically have exponentially many local optima, yet good solutions often appear after a few restarts.

Simulated annealing

Hill climbing never goes downhill, so it gets stuck; a pure random walk is complete but glacial. Simulated annealing interpolates, borrowing from metallurgy (heat, then cool slowly to reach a low-energy crystal). At each step, pick a random move; accept it if it improves things, otherwise accept it with probability eΔE/T — worse moves are accepted less often the worse they are (ΔE) and less often as the temperature T falls on a schedule. Shake hard early (escape local optima), gently later (settle into a good one). If T decreases slowly enough, the global optimum is reached with probability approaching 1. Heavily used since the 1980s for VLSI layout, factory scheduling, and airline scheduling — and still a staple in chip-design flows today.

Local beam search

Keep k states, generate all their successors, keep the best k overall. Not k independent hill-climbs: the k states share information — resources flow to the branches making progress ("come over here, the grass is greener"). Danger: the k states cluster onto one hill. Stochastic beam search fixes this by sampling successors with probability proportional to their value — natural-selection-flavored.

Genetic algorithms

Stochastic beam search with sexual reproduction. Maintain a population of states encoded as strings; score each with a fitness function; select parents with probability proportional to fitness; produce children by crossover (splice two parents at a random point) and mutate each with small probability. For 8-queens: a state is a string like 32752411 (queen row per column); fitness = number of non-attacking pairs (max 28); crossing 327|52411 with 247|48552 yields children mixing the two board halves. The hoped-for magic is that crossover combines independently-evolved useful blocks (schemas — e.g., a good arrangement of the first three queens) into wholes — which works exactly when the encoding places related traits adjacently. Early population diversity makes GA behavior exploratory; convergence later resembles stochastic hill climbing. Honest appraisal, then and now: GAs are appealing and occasionally effective (circuit layout, job-shop scheduling), but it remains debated when/why they beat simpler restart-based methods; in modern practice, gradient methods and simulated annealing usually win where they apply, with evolutionary methods reserved for non-differentiable, structure-rich spaces.

Checkpoint · 3.1
  • When only the final state matters, drop the paths: local search = current state + neighbors + objective, O(1) memory.
  • Enemies: local optima, plateaus, ridges. Weapons: sideways moves, random restarts (14%→94% on 8-queens), simulated annealing (probabilistic downhill moves under a cooling schedule), beam search (k communicating states), genetic algorithms (crossover of building blocks).

3.2Local Search in Continuous Spaces

Real environments are continuous — infinitely many successors, so "try each neighbor" fails. Example: place 3 airports in Romania minimizing the sum of squared distances from each city to its nearest airport; the state is six real numbers (x₁,y₁,x₂,y₂,x₃,y₃), and the objective f is a smooth function of them. Options:

  • Discretize: move each coordinate by ±δ; run ordinary local search over the resulting grid (12 neighbors here).
  • Gradient ascent/descent: compute the gradient ∇f (vector of partial derivatives) and step along it: x ← x + α∇f(x). The step size α is a genuine nuisance — too small crawls, too large overshoots. Line search extends the step until f stops improving. If f isn't available in closed form (e.g., the "objective" is a simulation), use empirical gradients — probe nearby points. Note the airports objective is only piecewise smooth: the gradient changes form whenever a city switches to a different nearest airport, so updates apply "as long as the assignment doesn't change."
  • Newton–Raphson: use second-derivative information — x ← x − Hf−1(x)∇f(x), where H is the Hessian matrix of second partials — to jump toward where the gradient is zero. Fewer steps, but the Hessian has n² entries, so high dimensions demand approximations (quasi-Newton methods).

Everything from 3.1 still applies: continuous landscapes have local optima, ridges, and plateaus too, and random restarts plus annealing remain the standard antidotes. High dimensionality just makes the landscape lumpier. Two special cases have exact theory: constrained optimization with linear constraints and objective is linear programming (feasible region = convex polytope; poly-time solvable); more generally, convex optimization problems are efficiently solvable even with thousands of variables.

2026 update

This little section became the engine of the deep-learning era: training a neural network is gradient descent on a continuous landscape with millions-to-trillions of dimensions, with the gradient computed by backpropagation, step sizes managed by adaptive optimizers (momentum, Adam), and stochasticity (minibatches) playing the annealing role of escaping bad regions. The vocabulary of this section — local minima, plateaus, learning rates, line search — is daily working language in ML.

Checkpoint · 3.2
  • Continuous spaces: discretize, follow the gradient (α = step size; line search helps), or use Newton–Raphson (Hessian) for faster convergence.
  • Linear/convex problems are solvable exactly and efficiently; general landscapes still need restarts and annealing.

3.3Nondeterministic Actions: Contingency Plans and AND–OR Search

When actions have uncertain outcomes, a fixed action sequence no longer suffices — percepts finally matter during execution, telling the agent which outcome actually happened. Solutions become contingency plans: branching strategies with if–then–else structure.

Worked example · The erratic vacuum world

Modify the vacuum: Suck on a dirty square cleans it and sometimes also cleans the adjacent square; Suck on a clean square sometimes dumps dirt. The transition model now returns a set of possible result states, e.g., from state 1 (both dirty, agent at A): Suck → {5, 7} (either just A cleaned, or both). A working solution must branch: [Suck, if State = 5 then [Right, Suck] else []].

Search trees for such problems are AND–OR trees: at OR nodes the agent chooses one action (ordinary branching); at AND nodes nature chooses the outcome, and the plan must handle every possible resulting state. A solution is therefore a subtree that (1) has a goal at every leaf, (2) picks one action at each OR node, and (3) covers every branch at each AND node. The recursive algorithm alternates OR-search (try each action; succeed if any works) and AND-search (recurse into each outcome; succeed only if all work), returning failure on any path that revisits a state — which guarantees termination in finite spaces, and is safe because if a plan existed from the earlier occurrence, it works there instead.

Cyclic solutions: try, try again

Now make movement slippery: Left/Right sometimes fails to move the agent. No acyclic plan exists (you can never guarantee arrival), but a cyclic plan does: keep moving Right until you observe you're in B — expressed with a label and loop, [Suck, L1: Right, if State = 5 then L1 else Suck]. Such a plan is a solution provided every outcome the environment can produce eventually occurs — i.e., failures are flaky, not adversarial. If the "slipping" might actually be a permanently broken wheel, retrying forever is wrong, and no finite plan can distinguish the two cases without better observations — a preview of why probabilistic reasoning and learning are eventually needed.

Checkpoint · 3.3
  • Nondeterminism: Result(s, a) returns a set of states; solutions become contingency plans.
  • AND–OR search: agent picks at OR nodes; the plan must cover all branches at AND nodes; loop-checking guarantees termination.
  • When failure can repeat, cyclic "retry" plans work — assuming failures are transient, not systematic.

3.4Partial Observability: Searching in Belief Space

The key idea

When the agent can't see the full state, it maintains a belief state — the set of physical states it might be in given its history of actions and percepts. Then it searches in belief space, where states are belief states, and the belief space is fully observable to the agent (it always knows what it believes). Solutions are again action sequences (or contingency plans over percepts).

Sensorless (conformant) search

No sensors at all — yet problems can still be solvable, and sensorless plans are valuable because they avoid sensing costs entirely. In the deterministic vacuum world with unknown location and dirt, the initial belief state is all 8 physical states. Then: Right → the agent must be in B (belief shrinks to 4 states); Suck → B is clean (2 states); Left, Suck → belief = {7}: everything clean, location known. Actions coerce the world into knowable states even though nothing was ever observed. (Real-world instance: orienting a machine part with a fixed sequence of tilts/barriers, no camera required.)

Mechanically, the belief-space problem is built from the physical problem: belief states are subsets of physical states (2N candidates — the blowup to fight); an action maps a belief b to the union of Result(s, a) over s ∈ b (a prediction step; with nondeterminism, union over all outcomes too); the goal test requires all states in b to be goal states; incidentally, if an action sequence solves belief state b, it solves every subset of b — so a solver can prune any belief state that's a superset of an already-solved one. Main practical obstacle: belief states are huge objects. Remedies: compact symbolic descriptions instead of explicit sets, or incremental algorithms that find one solution for the first physical state and check it against the rest, failing fast when a candidate breaks.

Searching with (partial) sensing

With observations, the belief-state transition has three stages: predict (apply the action: b̂ = all possible results), possible percepts (which observations could arrive in b̂), and update (for each percept o, keep only the states in b̂ consistent with o). Percepts can only refine prediction — each updated belief is a subset of the prediction. Because different percepts lead to different updated beliefs, the problem is nondeterministic from the planner's perspective — so solve it with exactly the AND–OR search of 3.3 over belief states; solutions are contingency plans branching on percepts (e.g., local-sensing vacuum: [Suck, Right, if Bstate = {6} then Suck else []]).

The execution-time half of this — maintaining the belief state as actions and percepts stream in — is monitoring / filtering / state estimation: b′ = Update(Predict(b, a), o), computed forever. It is the core function of any agent in a partially observable world (Kalman filters, robot localization, and particle filters are its probabilistic descendants).

Worked example · Robot localization

A robot in a known maze with a 4-direction obstacle sensor, but no idea where it is, and movement that may skip randomly. Percept NSW (obstacles north/south/west) is consistent with exactly 4 maze cells — the belief state after one observation. It moves Right; the prediction step smears each candidate rightward; a second percept NS then collapses the belief to a single cell. Two sensing steps: localized. This exact predict–update loop (with probabilities attached) is how every robot vacuum and warehouse robot localizes today.

Checkpoint · 3.4
  • Belief state = set of possible physical states; search belief space, which is fully observable by construction.
  • Sensorless plans coerce the world into known configurations; goal test = all members are goals; subsets inherit solutions.
  • With sensing: predict → possible percepts → update, solved by AND–OR search; the runtime version is filtering/state estimation.

3.5Online Search and Unknown Environments

All methods so far are offline: compute a complete plan, then act. An online agent interleaves: act, observe, decide the next action. Mandatory when the environment is unknown (the agent doesn't know what its actions do or what states exist — exploration: a robot in a new building, a newborn learning to move), and valuable in dynamic or stochastic domains where planning for every contingency is wasteful — better to handle surprises as they occur.

Setup: the agent knows its available actions, its step costs, and the goal test, but discovers Result(s, a) only by doing a in s. Performance is measured by the competitive ratio: (actual path cost traveled) ÷ (cost of the optimal path it would take if it knew the map). Hard truths:

  • An adversary argument shows no bounded competitive ratio is achievable in general — the environment can always arrange the goal to be where you looked last, and with general-shaped obstacles can force arbitrarily long detours.
  • Dead ends are worse: with irreversible actions, any algorithm can be led somewhere no goal is reachable — no algorithm avoids dead ends in all environments (whichever of two mirror-image traps your algorithm's first move commits to, the adversary presents that one). Practical online search assumes safely explorable spaces: some goal remains reachable from every reachable state.

Online DFS and why online A* isn't a thing

An online agent expands only the node it physically occupies — it can't teleport to a distant promising frontier node the way A* jumps around its priority queue. The natural fit is depth-first exploration: an online DFS agent records a result table Result[s, a] as it acts, tries untried actions at each state, and physically backtracks (executes the reverse action) when a state is exhausted — which requires actions to be reversible. Worst case it traverses every edge twice; that's optimal for pure exploration, but its competitive ratio for goal-finding can be arbitrarily bad since it may wander far from a nearby goal. (For goal-finding depth, iterative deepening adapts and is optimally efficient in uniform trees.)

Random walks and LRTA*

A random walk (pick a random applicable action, favoring untried ones) will find a goal eventually in any finite safely-explorable space — but "eventually" can be exponentially long, as easily-constructed traps keep walking the agent backward. Better: add memory + hill climbing. LRTA* (learning real-time A*) stores a current cost estimate H(s) for each visited state and, at each step:

  1. moves to the neighbor minimizing (step cost + H(neighbor)) — greedy, hill-climbing style;
  2. before leaving s, updates H(s) to that minimum — so if s turned out to be in a local dip, its estimated cost rises, "flattening out" the local minimum so the agent won't be permanently trapped there;
  3. assumes unexplored actions lead directly to the goal at cost h — optimism under uncertainty, which systematically drives exploration of unknown territory.

LRTA* is complete in finite, safely-explorable spaces (unlike plain hill climbing, whose "restart" trick isn't available when you can't teleport); it can take O(n²) steps over n states in the worst case, but usually far fewer. It is a member of the reinforcement-learning family — its H-updates are a deterministic ancestor of value-function learning, and "optimism under uncertainty" remains a central exploration principle in modern RL.

Checkpoint · 3.5 (end of Unit 3)
  • Online search interleaves planning and acting; required for unknown environments; scored by competitive ratio (unboundable in general).
  • Irreversible actions ⇒ dead-end risk no algorithm fully avoids; assume safely explorable spaces.
  • Online DFS explores with physical backtracking; LRTA* = hill climbing + learned cost table + optimism, complete where hill climbing isn't, and the bridge to reinforcement learning.

4.1Formulation Drills

Worked example · The crevasse-crossing puzzle

The lecture's signature example is the classic river-crossing puzzle in lunar dress: an astronaut must ferry a goose, grain, and a fox across a crevasse in a rover that carries the astronaut plus at most one item. Left unsupervised, the goose eats the grain and the fox eats the goose. Formulation:

  • States: which side of the crevasse each of {astronaut, fox, goose, grain} is on — 2⁴ = 16 conceivable states, minus the forbidden ones (goose+grain alone; fox+goose alone).
  • Operators: Move(astronaut) alone, or Move(item, astronaut) — cross with one item.
  • Initial / goal: all four above → all four below.

Drawing the full state graph (the lecture does, over two slides) reveals the solution almost mechanically — the safe states form a narrow corridor. One solution: take the goose over, return empty, take the fox over, bring the goose back, take the grain over, return empty, take the goose over again. The "aha" — moving something backward — falls out of blind graph search with no cleverness at all. That's the point of the lecture's slogan contrasting simple with trivial: early AI's dream of universal problem-solving methods works because simple ≠ trivial; a dumb systematic search solves puzzles that stump people.

Two more formulation sketches

  • 8-puzzle, formalized: states = an integer location for each tile and the blank (the slide's teasing "AND …??" — you must track the empty square for the operators to be well-defined); operators = move the blank up/down/left/right. Same lesson as Unit 2.2: the operator set is smallest when you think of the blank as the thing that moves.
  • Route finding (the lecture's "home to MIT" map): states = intersections; operators = road segments; the exact formulation the drills ask you to produce for any new problem — states? operators? initial and goal state? is the reflex to build.

Languages for states and operators: STRIPS

For tasks too rich to enumerate by hand — the lecture's example is the Apollo 13 crew assembling the improvised CO₂-scrubber rig — you need a language for describing states and operators. In the STRIPS planning language, a state is a conjunction of logical facts ((on-table a), (clear b), (empty arm)); a goal is a partial state (any state satisfying (connected a b) ∧ (connected b c) counts); and each operator (e.g., pickup hose) has a precondition (facts that must hold to apply it) and an effect (facts added and deleted). This is the factored representation from Unit 1.5 put to work: instead of naming 10²⁰ states individually, a handful of predicates and operators generates the state space. (STRIPS descendants — PDDL — remain the standard interface of automated planners today.)

Checkpoint · 4.1
  • The formulation reflex: states? operators? initial state? goal? — apply it to any new problem.
  • Systematic search makes "insight" puzzles mechanical (goose goes back across!).
  • STRIPS: states as fact-sets, goals as partial states, operators as precondition + effect — a compact language that generates huge state spaces.

4.2Graph Vocabulary, Precisely

Unit 2 used graphs informally; the lecture pins the terms down. A graph is G = ⟨V, E⟩: a set of vertices and a set of edges. Mapping to search: state ↔ vertex, operator ↔ edge.

Edge & vertex terms
  • Directed graph (one-way streets): each edge ⟨t, h⟩ has a tail and head vertex. Undirected (two-way): edges are unordered pairs; endpoints are neighbors / adjacent.
  • Degree of a vertex = number of incident edges; directed graphs split this into in-degree and out-degree.
Graph-level terms
  • Connected: a path exists between every pair of vertices; strongly connected (directed): a directed path between every pair.
  • Complete: all vertices pairwise adjacent. A subgraph is a vertex subset plus the edges among them; a clique is a complete subgraph.

A path is a vertex sequence ⟨v₁,…,vₙ⟩ where each successive pair is an edge; a cycle is a subpath whose start = end; a simple path has no cycles (no repeated vertices). A tree is a graph with exactly one undirected path between any two vertices — equivalently, every vertex has in-degree 1 except the root. Family-tree vocabulary carries over: parent, child, siblings, ancestors, descendants, leaf, branch.

The formal search problem

Input: S = ⟨g, S, G⟩ — a graph, a start vertex, a goal vertex. Output: a simple path from S to G. The search tree of a graph denotes all its simple paths from S — which is why tree enumeration is complete (every solution appears), systematic (nothing visited twice along one path), and sound (everything returned is a real path).

Checkpoint · 4.2
  • State space = graph; solution = simple path from start to goal; search tree = the set of all simple paths, unrolled.
  • Vocabulary that recurs everywhere later: directed/undirected, degree, connected/complete, subgraph/clique, tree/root/leaf.

4.3One Algorithm to Rule Them All

The lecture's cleanest contribution: DFS and BFS (and later, best-first and A*) are the same algorithm with one line changed. Maintain a queue Q of partial paths (each stored head-first, e.g. ⟨D, A, S⟩ = the path S→A→D whose head is D):

// Simple Search Algorithm — the template for everything
1. Q ← { ⟨S⟩ }                          // one partial path: just the start
2. if Q empty: fail. Else pick partial path N from Q
3. if head(N) = G: return N            // goal reached
4. else: remove N from Q;
        extend N one step to each child of head(N);
        add the extensions to Q; goto 2

// The strategy is entirely in step 4's "add":
DFS:  add extensions to the FRONT of Q   // stack → dive deep
BFS:  add extensions to the BACK  of Q   // FIFO  → sweep levels

Two refinements, with reasons:

  • Visited list (cycle handling). Without it, the same vertex heads many partial paths (the lecture's graph reaches C by three routes) and worst-case work explodes into the number of simple paths — exponential. Fix: keep a Visited set; don't enqueue an extension whose head was already visited, and add each head's children to Visited as you enqueue them. Correctness: any goal reachable from a vertex's second visit was reachable from its first. Efficiency: each vertex now heads at most one enqueued path. This is exactly Unit 2.3's explored set, derived from scratch.
  • Where to test the goal. The template tests when a path is picked (step 3), not when it's generated. Testing at generation would end sooner and is fine for DFS/BFS — but it's wrong for optimal searches like A* and uniform-cost, where a goal path that appears early may not be the cheapest (recall UCS's late goal test in Unit 2.4). The lecture keeps the pop-time test for uniformity with what comes next.

The lecture's taxonomy of what "comes next" — a preview map of the whole field:

ClassAlgorithmsWhat guides the pick from Q
Blind (uninformed)Depth-first, breadth-first, iterative deepeningNothing — systematic exploration until the goal appears
Heuristic (informed)Hill-climbing, best-first, beamA heuristic "goodness" score of the head node
Optimal (informed)A*, branch & boundA path-length measure — find the shortest path
Checkpoint · 4.3
  • One template: pick a partial path from Q → goal-test its head → extend → re-add. Front-of-Q = DFS; back-of-Q = BFS; priority order = A* and friends.
  • Visited list = completeness + efficiency in cyclic graphs; goal-test at pop, not generation, to stay compatible with optimal search.
  • Judge any instance on: time, space, soundness (returned answers are correct), completeness (finds one if one exists).

4.5From Continuous Robots to Graph Search: Motion Planning

How does a physical vehicle in continuous space use any of this? The lecture's three-step pipeline — still the backbone of robot motion planning:

  1. Build the configuration space (C-space). A translating (non-rotating) vehicle with real shape is awkward to plan for; instead, inflate every obstacle by the vehicle's shape and shrink the vehicle to a point. Planning a point through the inflated obstacles is exactly equivalent to planning the real vehicle through the real obstacles — and vastly simpler. (With rotation or robot arms, the C-space gains dimensions — one per degree of freedom — but the idea is identical.)

  2. Discretize into a roadmap. Convert the continuous C-space into a graph. The lecture surveys the classic options:

    • Visibility graph: vertices = start, goal, and obstacle corners; edges = every pair of vertices that can "see" each other (straight line, no obstacle). Shortest paths hug obstacle corners — optimal in 2-D, but paths graze obstacles (uncomfortable for real robots) and the construction scales poorly.
    • Voronoi diagram: edges equidistant from the nearest obstacles — maximally safe paths, at the cost of extra length.
    • Cell decomposition: tile free space with cells — fixed-size grid (simple, resolution-limited), variable-size/quadtree (finer near obstacles), or exact decomposition (cells exactly fill free space) — and connect adjacent cells.

  3. Search the graph — with A* (Unit 2.5). Continuous problem in, discrete optimal path out.

Scaling up: sampling. Explicit roadmaps die in high-dimensional C-spaces (a 7-joint arm lives in 7-D). Rapidly-exploring Random Trees (RRTs) instead grow trees by sampling random points and extending the nearest tree branch toward each sample — often one tree from the start and one from the goal until they meet. RRTs (and cousins like PRM and RRT*) remain the workhorses of manipulation and autonomous-vehicle planning today.

Plans vs. policies. One more lecture idea, pointing forward: a path is fragile — drift off it and it says nothing. A policy π maps every state to an action (equivalently, a shortest-path tree from all vertices to the destination), so execution errors are self-correcting: wherever you end up, the policy already knows the best next move. Policies are how search-based planning meets the online/error-prone reality of Unit 3.5 — and they're the central object of Markov decision processes and reinforcement learning.

Checkpoint · 4.5 (end of Unit 4)
  • Motion-planning pipeline: C-space transform → roadmap (visibility / Voronoi / cells) → A*.
  • High dimensions ⇒ sample, don't enumerate: RRTs.
  • A policy (action for every state) beats a single path when execution is imperfect — the bridge to MDPs and RL.

Final Synthesis

The whole module on one page
The complete argument, in order
  • Agents map percept sequences to actions; rationality = maximizing expected performance given percepts and knowledge. Specify tasks with PEAS before designing anything.
  • Environment properties (observability, agents, determinism, episodicity, dynamism, continuity, knownness) dictate the required architecture: reflex → model-based → goal-based → utility-based, wrapped in learning.
  • In friendly environments (deterministic, observable, static, known), goal-based agents can search: formulate a five-part problem, grow a tree over the state space, use graph search to kill redundant paths.
  • Uninformed: BFS (optimal, memory-hungry), UCS (optimal for any positive costs), DFS (linear memory, no guarantees), IDS as the blind default, bidirectional when applicable.
  • Informed: A* with admissible/consistent h is complete, optimal, and optimally efficient; memory limits push toward IDA*/RBFS/SMA*. Heuristics come from relaxations, pattern databases, and learning — better h means exponentially less search.
  • When only the state matters: local search — hill climbing + restarts, simulated annealing, beam search, genetic algorithms; in continuous spaces, gradients and Newton steps (the mathematical bedrock of modern deep learning).
  • Remove determinism: AND–OR search yields contingency (and cyclic) plans. Remove observability: search over belief states with predict–update; runtime version is state estimation. Remove the map itself: online search — online DFS, LRTA*, optimism under uncertainty — the doorway to reinforcement learning.
  • In practice: everything is one queue-of-partial-paths template (front = DFS, back = BFS, priority = A*), cycle detection via a visited list is non-negotiable, STRIPS-style languages generate huge state spaces compactly, and continuous robot problems become graph search via C-space → roadmap → A* (or RRTs when dimensions explode) — with policies instead of paths when execution is error-prone.
Exit ticket: five questions to test yourself (answers inside)

1. Why can a rational agent perform a poor-outcome action and still be rational? Rationality maximizes expected performance given available percepts — actual outcomes can be unlucky. Omniscience is not required.

2. Why is IDS preferred over BFS for large unknown-depth problems? Same completeness/optimality (unit costs) and O(b^d) time, but O(bd) memory instead of O(b^d); regeneration overhead is only ~b/(b−1), e.g., ~11% at b = 10.

3. State A*'s optimality condition and the reason. h admissible (tree search) or consistent (graph search); then f never decreases along paths and A* expands nodes in nondecreasing f order, so the first goal expanded is optimal.

4. Why do random restarts fix hill climbing offline but not online? Offline, a restart is free — jump to a new random state. Online, the agent physically occupies a state and can't teleport; LRTA* instead raises cost estimates of visited states to escape local minima in place.

5. Why is belief-space search "fully observable"? The agent always knows its own belief state exactly — uncertainty about the world becomes certainty about a set, so classical machinery applies to the (bigger) belief space.
